# Online lobby replication

The development transport uses wire version 8. Both peers must use the same executable; older wire versions are rejected during handshake.

`Session` now owns the lobby roster on the host and replicates accepted snapshots to the client. Name, character, color and readiness requests carry a monotonically ordered request identifier. Client requests never carry a target peer identifier: the connection determines which player may be edited. Requests are acknowledged explicitly, so queueing a request does not imply the host accepted it. An occupied color or invalid name is rejected without disconnecting the player or mutating the accepted roster.

Snapshots contain bounded, canonical UTF-8 names, character choices, unique palette entries, readiness and a revision. The decoder rejects duplicate peers/colors, malformed names, nonzero unused entries, invalid enums and inconsistent locked rosters. The host rejects clients attempting to send authoritative snapshots; the client rejects replies without a matching outstanding request and regressing snapshots. Appearance changes invalidate readiness for everyone.

The wire format can represent sixteen roster entries. **The current gameplay session still has two input lanes and advertises capacity two.** Neither the palette nor the snapshot codec increases playable capacity. The native menu displays the accepted roster and supports editing names and explicitly choosing guest readiness. Actual per-actor appearance/name labels, independent additional-player input, level/death ownership and relay-backed Internet matchmaking remain separate work. The public demo keeps its online entry disabled until those paths are ready.

Regression coverage uses the actual TCP session on loopback to verify default roster exchange, duplicate-color rejection, same-character/different-color acceptance, assigned-peer name editing, invalid-name rejection and readiness invalidation. Separate fragmented-packet tests cover sixteen-entry snapshots and malformed roster rejection. These tests do not establish sixteen-player gameplay or Internet connectivity.

The existing native-menu start barrier now sends client readiness through the same host-owned roster. The host freezes that roster and sends its locked snapshot before the native Start message. Both boot owners verify the same locked snapshot before handing the live session to gameplay. Later profile requests are rejected as locked, and changing appearance before Start invalidates the readiness agreement.


## Native lobby profile controls

The native GFx lobby shows the accepted roster once both machines have connected and installed the shared save. Select **Name** to edit the local player name in a native input field. Enter/A commits; Escape/Back cancels. Window character events feed a bounded Unicode editor; the native menu reads its text and selection through the numeric GFx bridge. Committing follows the same host validation/acknowledgement path as other profile requests. Keyboard arrows, Home/End, selection, Backspace/Delete, Ctrl+A and bounded Unicode paste operate locally without emitting game bindings. The field is disabled while a request is pending or the roster is locked. The accepted name is displayed, so a rejected edit does not appear as a successful speculative change.

Guests explicitly choose **Ready** and can revoke it before the host starts. Merely polling or opening the lobby no longer re-arms the guest. The private automatic native-menu QA path retains automatic readiness for its two-machine test. Selecting Start is the host's readiness confirmation. Character/color controls are not exposed as playable options until those choices can be applied to the native actors.

The authored ActionScript build checks the resulting GFx by decompiling it again, verifies the profile-control bridge markers, and requires exactly one changed native class bytecode tag with all unrelated assets unchanged. This is a compile/structure check; live focus, controller text entry and layout still need gameplay validation. Captured keyboard keys remain owned until release, including after committing or cancelling, so autorepeat cannot activate another menu item. Losing window focus cancels the draft. Text, caret and selection readback use one snapshot per refresh to avoid mixing UTF-8 bytes while typing. The demo gate also covers the new bridge IDs, including name-edit commit/cancel, without opening sockets or publishing a session.
