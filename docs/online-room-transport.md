# Online room transport and native frames

The development `Room` transport supports a host plus fifteen guests. The normal native lobby/startup still uses the two-player `Session` path. This component has not enabled sixteen-player gameplay or Internet matchmaking in the public demo.

The host assigns connection-bound peer IDs 1..16. Input packets cannot specify a different sender. Host capacity comes from the actual gameplay adapter. The original `Host`/`Join` API requires matching nonempty build, content, checkpoint and invitation identities and an already-installed shared checkpoint. Explicit `HostWithCheckpoint`/`JoinWithCheckpoint` bootstrap now transfers the host's frozen save on that same room connection. Only that explicit join mode permits a missing or different local checkpoint; every other identity field must match. Normal native startup has not adopted this bootstrap yet.

The host owns names, unique colors and readiness. Start freezes the accepted roster, closes admission and enters Loading. Each native gameplay adapter must explicitly report completed world loading and actor admission with the same nonzero world token. Only the host can activate the frozen room after every participant reports that token. No input, neutral seed or simulation frame is available beforehand. A mismatched token or startup exceeding 180 seconds stops the room; heartbeats cannot extend this absolute deadline. The token is a caller assertion, not a substitute for implementing native load/admission validation.

A name/readiness edit arriving after Start receives an ordered Locked reply without disconnecting or changing that roster. Guests leaving the lobby free their IDs/colors, invalidate readiness and leave the host available for another guest. Losing a participant during loading or a running match stops the room until a negotiated removal/respawn protocol exists.

Every player submits one command for each consecutive tick. The host waits for the entire frozen roster, then broadcasts the same frame to all participants. Clients validate their own echoed input, including exact floating-point bits. A bounded 64-tick window and byte/packet/queue limits prevent unlimited buffering. Heartbeats and a 15-second running progress deadline stop lost/stalled sessions after activation. A coordinated in-game pause and subsequent level-transition policy is still needed.

Commands contain native interpreted Movement values, a normalized ground-plane view direction, raw controller intent, and an authoritative logical actor incarnation. Room wire version 4 retains checkpoint bootstrap and native Jump press/release events, and explicitly negotiates optional synchronized raw native bootstrap. Jump carries a binding-derived button mask and consecutive event sequence numbers. Held ticks carry no new edge. Both sender and receiver validate complete event batches before committing stream history; duplicates, gaps, changed masks, source downgrades and forged echoes reject. A maximum-size 64-frame, sixteen-peer burst is covered by the receive budget. Raw stick axes cannot substitute for interpreted movement. Source/epoch/basis validation is shared with the native frame coordinator. The current frozen transport epoch is 1; synchronized respawn and epoch changes remain future integration.

### Synchronized raw native startup

The original direct `Start` → `WorldReady` path remains available. The host may instead select `StartNativeBootstrap`, which freezes the same installed/ready roster and enters Loading with an explicit negotiated raw-start mode. Callers report the same nonzero loaded single-player world token using `BootstrapWorldReady`. This assertion does not require human-controller or interpreted-input producer eligibility yet. All frozen peers must match before the host opens `Bootstrapping` at the original identity first tick, with zero raw input delay.

`RoomBootstrapFrame` contains only its tick, frozen player mask and raw `Pad` values. `SubmitBootstrapPad` accepts one current-round sample per peer; there is no future raw window. The authoritative frame waits for every sample, and each client validates its own exact echoed controller input. `PeekBootstrapFrame` retains the pending frame, and `TakeBootstrapFrame` consumes it once. These frames never appear through normal `PeekFrame`/`TakeFrame`, never satisfy `SubmitLocal`, and never claim to be interpreted Movement.

After completing that native tick, each caller reports `CompleteBootstrap(tick, ready_for_gameplay, observation_digest)`. The nonzero digest is a caller assertion of the completed native observation. The host waits for every completion and requires identical digests. A false readiness vote authorizes exactly one ordered Continue round. Votes and raw samples are reset for that round. All true votes on the same completed tick authorize interpreted gameplay at the next tick. The original negotiated gameplay delay is then seeded with neutral native commands beginning at that new first gameplay tick. The identity first tick still records the original bootstrap start; consumers use the gameplay timeline after cutover.

Continue/Activate controls bind the loaded-world token, frozen revision/mask, completed/next tick and observation digest. Clients require their own consumed and completed proof; activation additionally requires their own true readiness vote. Stale, duplicate, future or forged controls/proofs reject. Raw input after gameplay activation rejects, and no pending raw frame is carried into gameplay. The absolute 180-second startup deadline covers both Loading and every bootstrap round; heartbeats and continued native updates cannot extend it. Disconnect stops the frozen room. Tick exhaustion and an overflowing delayed gameplay start fail instead of wrapping.

Transport does not change synchronized controls, native RNG ownership, native joins or actor bindings. The native runtime owner must publish the agreed raw Pads, finish the native update, compute the canonical observation, and perform this cutover at its completed-update boundary. The transport fixture covers sixteen sockets with a delayed last loader/completer, multiple fresh readiness rounds, neutral gameplay seeding, first interpreted command, malformed input/proofs, own-echo tampering, authority checks, startup deadlines and uint64 exhaustion. It does not itself establish that production native startup uses this owner.

### Checkpoint bootstrap ownership

The caller runs `PackCheckpoint` on a worker, validates its result and supplies one immutable `CheckpointBundle` to the host. All guests share that host-side buffer; each socket queues at most 16 chunks of up to 1 KiB per poll, subject to its byte cap. Slow guests cannot monopolize another guest's transfer. Announcements are bounded by the existing 33 MiB bundle limit. Offsets, chunk sizes, completion length, header identity, directions and message ordering are checked before accepting a complete download.

Transport performs no installation or save-path selection. A guest obtains `DownloadedCheckpoint()`, runs `InstallCheckpoint` on a worker using `identity().checkpoint` and a new isolated directory, then calls `ConfirmCheckpointInstalled(result.installed)` on the room owner thread. The worker validates archive entries, file hashes and the checkpoint tree digest. The boolean is an explicit caller assertion of that result, not proof that transport inspected a filesystem. The installed digest is mutually acknowledged with Installed → Ready → Ack before the guest can ready or the host can start. `checkpoint_peers()` exposes host-side progress and installed status for every admitted peer. A worker failure closes that guest; the pre-start host remains available and releases its slot.

Only actual newly received bytes renew the 120-second transfer/installation progress deadline. Socket buffering, heartbeats and repeated progress acknowledgements do not renew it. Each guest owns at most one bounded download, and no normal save/content path is passed into transport. All peers completing installation is separate from lobby readiness and the subsequent native-world `WorldReady` barrier. The CPU fixture uses real four-peer TCP, a worker-packed save, independent worker installations, an unpolled slow guest, slot reuse, malformed streams, a corrupt-payload worker rejection and a stalled installation with live heartbeats. These fixtures pass in the focused canonical-executable suite; they do not assert that the normal native lobby uses Room yet.

`OwnedMovementFrames` maps logical room peers/epochs to separately validated native handles and controller generations. Preflight checks the entire frame before native callbacks. Deliver stages all view bases, invokes original Mickey Movement handlers exactly once for every owned actor, then delivers ordered native Jump edges; a partial native failure faults the coordinator and forbids retrying/advancing the world. Finish advances its tick only after the caller completes the native world update. The caller separately publishes the two retail controller lanes. Extra actors currently reject unsupported button/brush/tool intent instead of silently claiming those controls work.

The intended live boundary is after native synchronized join and before original `829ED310` world update. `Room::PeekFrame` allows native preflight without advancing transport consumption. The caller consumes with `TakeFrame` only after successful all-actor admission, then delivers once and finishes after the native tick. The current fixture exercises real TCP room frames through the coordinator and original native action/controller code, with distinct peer view bases, explicit neutral release, and a closed native readiness gate that must retain the exact pending input. Its controlled native continuation sink excludes physical contacts and a complete gameplay world. Normal startup has not been switched to this path.

### Native input production order

The primary application vtable is `8210A0B8`, installed by constructor `829E7DA0`. `8210A0D4` is its interior actions slot, not the table base. The original loop `83075AA0` calls frame virtual+32 (`829EC348`); that frame calls world virtual+48 (`829ED310`) and post-update virtual+52 (`829D95B8`). Inside the world function, `830748B8` calls device refresh virtual+24 and actions virtual+28 (`829E9E30`). The latter dispatches `827C75B0`, which evaluates action math and invokes listeners.

Consequently, current-tick native action callbacks do not exist yet at the existing pre-world network admission boundary. Waiting there for a callback produced later in that same world tick would deadlock. Returning from the middle of the original world update and retrying would repeat earlier services. Native local command production must evaluate the actual selected action math independently before admission, or use an explicitly negotiated delayed-input pipeline. `82767CD8` is a save-manager update, not an input phase, and must not be repurposed.

The live startup also has a short authored UI-to-game context transition after actors exist: there is temporarily no eligible Movement action. Discovery must report not-ready, rather than inventing interpreted neutral. Room adoption must retain synchronized native initialization during that interval, as the existing Session path does before asynchronous P2 activation; independently warming each world until a binding appears would reintroduce AI/RNG divergence. Pre-tick discovery removes the callback dependency, but does not replace that bootstrap policy.

`online_local_movement.cpp` implements the independent math path for the observed retail Mickey Movement binding. An explicit game-thread lease enables observation at the ordinary Mickey listener entry, after owned-actor quarantine and character-swap suppression. Read-only pre-tick discovery can also establish a binding directly from the selected player and active/default native event lists, without waiting for a callback inside the world tick. Multiple valid Movement routes are rejected as ambiguous. Discovery does not fabricate callback provenance; the observation route retains its exact native return-address guard. Access revalidates the current registry, resolved player handle, controller/listener, active event context, exact action membership/shape, native profile device selection and device ranges. It rejects stale or unsupported bindings. It does not claim that a missing binding is neutral input.

Production uses the original `827C5990` action math on preserved scratch with a scoped left-axis query. The authored movement records are Y-first (`02400018`, destination0), then X (`02400017`, destination3); response settings remain native. Logical action-player indices and physical input-device indices are resolved separately through the original profile path.

`ProduceNativeLocalRoomMovement` assembles interpreted movement, the full Pad, an explicitly supplied authoritative actor incarnation, and the sender's ordinary camera-reference forward direction. It invokes original `82783208` on a private copy of the Basic controller, through the original NiEntity WorldTransform dispatcher, to obtain the same positive X/Z projection and normalization used by the ordinary controller. Only the private copy receives native capture/cache writes. The real camera GUID/component identities are pinned; stale/reused references, captured transitions, alternate/scripted paths, failed queries and degenerate/nonfinite transforms reject. No network tick or actor incarnation is inferred from a guest pointer or local producer generation. The producer remains unarmed in ordinary gameplay until the Room owner is integrated; other actions, Oswald bindings and online lifecycle still need that integration.

### Native startup adoption

`OnlineRoomBoot` now joins preparation workers to the larger Room transport. It reuses the exact verified preparation worker used by `OnlineBoot`: installation fingerprints, retained-source checks, create-new private roots, checkpoint packing and host installation. Guests install immutable downloads on workers. The coordinator exposes profiles, unique appearance colors, readiness and per-peer progress; only the host can start. `TakeStarted` transfers a frozen `Loading` Room and its private save root exactly once. It does not assert that a native world or actor is ready. Its fifty-six-check fixture runs three actual peers through workers and lobby start, destroys the old coordinators, then verifies the retained sockets' explicit fixture-world barrier and authoritative frame. Failure and cancellation cases preserve normal campaigns.

Native joining now has an explicit `NativeJoinTick` core carrying the actual published-controls generation, complete two-lane retail frame and joining phase. It requires the same owner thread and current agreed native tick; foreign publication, stale generations, changed pads and duplicate/nested dispatch reject. The legacy Session adapter supplies the same context. A scoped accepted-context lease prevents a second ordinary Start-triggered join in that exact native tick, without changing offline calls. Native debounce timing includes the controls generation and keeps the original elapsed/reset callsite guards.

`NativeInitializationContext` owns the immutable negotiated identity and seed sequences independently of a transport. It arms before startup, binds after the prelaunch poller has stopped, and rejects foreign-thread, failed, unbound or exhausted requests. Per-player initialization cannot reseed inside an agreed timeline. Both retained native owners use this context.

The explicit raw initialization phase is now implemented and remains separate from interpreted Movement. OnlineRoomBoot can select it at host Start; native-menu preparation always negotiates shared native initialization. The normal lobby still uses the legacy owner, so this alone does not enable sixteen-player gameplay.

`RoomBootstrapGate` bridges the raw transport rounds to original retail controller publication. It permits neutral input and native player-two Start, caches a submitted round while waiting, and requires exact transport consumption before publishing. Complete observations authorize later rounds; disconnects, malformed intent or lost ownership halt the world and disconnect peers while retaining the last published controls until explicit teardown. Legacy and Room native owners cannot acquire the same lease. Generation-bound shutdown preserves a replacement controls owner.

The native simulation now routes Room initialization admission before original `829ED310`, commits its exact retail lanes, starts the agreed native tick and invokes the scoped native join handler. Original post-update `829D95B8` still runs once when the next admission waits. The finish observer checks a caller-installed actor/producer readiness predicate, reads actual native gameplay observations and CRT counters, and submits their digest. No predicate means no gameplay-ready vote. Invalid observations stop initialization. At transport cutover the bridge advances only unused physical-sampler clocks, clears stale taps/wheel input, and preserves controls generation and RNG ownership. It then waits for the gameplay adapter instead of advancing as offline.

The focused suite includes 3,485 Room transport checks, 56 coordinator checks, 44 bridge checks and 31 retained native-owner checks. The bridge fixture uses three real connections and synthetic completed observations; it does not execute a native world. Scheduler regressions cover deferred outer completion and no offline advancement after cutover/failure.

### Retained native Room startup

`AdoptNativeRoom` retains the frozen loading Room through a prelaunch transport worker and its explicit handoff to the native simulation thread. The worker stops and joins before guest initialization is bound. Original profile selection and Continue use the agreed private checkpoint. The loaded-world barrier hashes the negotiated identity, actual native load destination and frozen roster. A completed copy waits without polling uncontrolled physical input while its peer finishes loading. The simulation attaches the raw bridge only at a completed-update boundary and retains its controls and RNG ownership until explicit shutdown.

`scripts/start-private-room-pair.ps1` opens two isolated instances of the canonical `beetleworx.exe`, transfers a copied checkpoint and invokes native Continue/co-op initialization. It sends no movement or camera input. The private probe discovers actual input bindings and evaluates neutral original movement math, but deliberately never asserts gameplay readiness. `-TraceInitialization` adds bounded native module-registration/initialization tracing; it is off by default. A verified fingerprint cache avoids scanning the same content twice within a pair without accepting caller-supplied hashes.

### Retail input selection and physical sources

The native Movement and Jump producers now explicitly select retail slot 0 or 1. Both require an actual human-controlled record, the existing admitted controller/listener types, that slot's authored action family and its own retained camera reference. The original unsigned-device APIs still require the sampled physical user to match the binding's native device. Selecting Oswald does not weaken those checks or register him as an extra actor.

`NativeRoutedPadSample` provides the separate guest routing path: the owning sampler polls the real local hardware index and seals its result against the current Room, selected binding, synchronized-controls generation and source tick. Typed producer overloads revalidate that proof before and after original native math. Hardware 0 can therefore supply canonical native device 1 without pretending the physical poll came from device 1. A route can arm at its own completed raw-bootstrap boundary without polling; samples require Running and the explicit gameplay sampler cutover. Replaced bindings, controls ownership, ticks or Room state invalidate cached proofs. This sender support still needs the retail gameplay receiver described below.

The original-code input fixtures pass 3,453 Movement checks, 475 Jump checks and 24 source-route checks. The source fixture uses real connected Rooms and a counted physical SDK driver: only hardware 0 is polled for the guest's native user 1. It covers cached ticks, wrong/expired proofs, unchanged strict-device rejection, foreign threads, Room disconnect, controls replacement and route teardown during an SDK poll. These are headless input-contract tests rather than proof of live received movement.

A paired native-level smoke test independently discovered both real retail bindings on both peers and evaluated original neutral Movement/Jump math using each character's own reference. Controller bytes and PPC context remained unchanged. All 206 shared recorded ticks matched, and all eight normal save/settings files retained their original hashes. The test sent no movement, events, gameplay commands or gameplay-ready vote; live source routing and received action replay remain unaccepted.

Still required before enabling this route in the public menu: resolve native divergence/startup failures, install the validated local hardware route in a complete gameplay owner, complete interpreted gameplay admission and action replay, synchronize actor lifecycle/death/level changes, and validate additional actors. The owned-extra coordinator intentionally excludes the two retail slots; they require their own validated replay leases and ordinary-input suppression so an agreed command is not applied twice. Running Room transport also needs an explicit completed-world observation proof barrier; `CompleteBootstrap` verifies initialization only. Relay-backed Internet connection, public discovery and Discord invitations remain separate unfinished work. No gameplay-ready predicate is installed by default, and the normal demo online entry remains disabled.
